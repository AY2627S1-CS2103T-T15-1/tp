Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete --id 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

UiManager implements Ui and creates the MainWindow. The main window creates a CommandBox, ResultDisplay, PersonListPanel, PersonDetailPanel, and StatusBarFooter. It also creates one HelpWindow, reused by the help command, Help menu and F1 shortcut. These visible components and PersonCard inherit from the abstract UiPart class, which loads their FXML layouts and provides access to their JavaFX roots.

PersonListPanel observes the filtered client list supplied through Logic and creates PersonCard objects for its list cells. PersonDetailPanel also creates a PersonCard for the selected client's header. It displays the client's notes, workout plan and appointments when present, together with up to four session records ordered by date, newest first. When there are no sessions, it displays an empty-state message.

CommandBox submits commands through a CommandExecutor callback supplied by MainWindow. The main window calls Logic.execute, displays feedback in ResultDisplay, and handles the returned CommandResult. A result containing a client switches to the detail panel; other successful commands return to the list unless they request help or exit. Failed commands display their error message and preserve the current panel.

The UI also contains supporting classes that do not inherit from UiPart. Each CommandBox owns one in-memory CommandHistory for recalling input with the Up and Down keys. HelpContent holds an immutable catalog of CommandSummary objects, which HelpWindow reads to build its command cards. The diagram omits JavaFX controls, the nested command callback interface and list-cell class to keep the component relationships readable.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Executing a delete command

The get all clients interaction abbreviates Model#getAddressBook().getPersonList(); the intermediate address-book object and result construction are omitted. The zero-match exception is also omitted.

DeleteCommand, like the other commands that act on one client (e.g. view, edit, note), extends PersonTargetedCommand. The parser turns --id 1 (or --name NAME) into a PersonSelector, and the command uses it to find the matching clients when executed. If exactly one client matches, the command acts on that client in executeOn. If several clients match, which can only happen with --name, no client is changed: the list is filtered to the matching clients, and the user is asked to choose one with --id. If no client matches, a CommandException is thrown (not shown in the diagram).

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

Model component

API : Model.java

The Model component,

  • stores Cindy's client data i.e., all Person objects (which are contained in a UniquePersonList object). Each Person has a unique PersonId, up to four Appointment objects, and any number of Session records. AddressBook also stores the next PersonId to give out, so IDs are not reused after a client is deleted. The exception is clear --confirm, which replaces the address book with an empty one, so numbering starts again from 1.
  • stores the custom groups (e.g. morning, rehab) as a list of Tag objects in AddressBook, in the order they were created. Every custom tag of a Person is also one of these groups, so a client can never be in a group that does not exist. gym and personal are built-in client types, not groups.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list, which is kept sorted alphabetically by name (case-insensitive) unless a command gives another order. list --today, for example, sorts clients by their earliest appointment today. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Long-form text

LongFormText preserves its supplied value exactly; its constructor does not interpret escape sequences. Storage uses these values directly, so loading and saving text preserves literal backslashes and actual line breaks.

ParserUtil#parseLongFormText requires outer double quotes and converts every backslash followed by a lowercase n into an actual line break. It does not provide an escape for a literal backslash followed by n: two backslashes followed by n become one backslash followed by a line break. Other backslash sequences remain unchanged.

LongFormText#toTypedText converts actual line breaks to \n but leaves existing backslashes unchanged. Converting stored text to command text and parsing it again therefore does not preserve values containing literal \n. This is a documented command-input limitation; see Long-form text limitations in the User Guide.

Storage component

API : Storage.java

The Storage component,

  • can save both Cindy's client data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

File locations

AppPaths#getHomeDirectory() in seedu.address.commons.util provides an absolute, normalized home folder. It resolves the location of its own code source through a URI so that spaces and other encoded characters in the path are handled correctly.

  • When packaged in a JAR, the home folder is the folder containing that JAR, regardless of the working directory.
  • When running compiled classes, such as through Gradle during development, the home folder is the working directory (normally the project folder).

MainApp resolves data/cindy.json and preferences.json against this home folder before constructing the storage objects. LogsCenter uses the same helper for its rotating cindy.log files and lock file. It escapes percent characters in the log path because FileHandler interprets them as pattern markers.

The application does not search another folder for existing data or fall back to another save location when writing fails. Moving a packaged application therefore requires moving its data folder and preferences.json alongside the JAR. These paths are anchored to the home folder; the helper does not enforce containment against symbolic links pointing outside it.

AppPathsTest#getHomeDirectory_packagedJar_usesJarFolderInsteadOfWorkingDirectory() packages the helper, logging class and a probe into a test JAR. It runs the probe in a separate JVM from a different working directory and verifies that the home folder and generated log are beside the JAR, with no files created in the launch directory. The JAR folder contains spaces and a percent character to cover URI decoding and log-pattern escaping. MainAppTest#defaultFilePaths_useAbsoluteDevelopmentHome() verifies the contact, preference and log paths for development runs.

Data-loading failures

JsonUtil#readJsonFile returns Optional.empty() only when the file does not exist. An existing file whose entire JSON value is null is rejected with a DataLoadingException, as are JSON read and parse failures. Although null is valid JSON syntax, it does not contain the object Cindy needs. The null-root check runs before Optional.of, preventing an unchecked NullPointerException.

For a missing client-data file, MainApp#initModelManager creates and saves sample clients. For an unreadable client-data file, including a null root, initialization instead leaves the model and logic unset. Starting the app shows the Unable to open Cindy recovery dialog with the data-file location and closes without opening the command window or replacing the file. A null root must not be treated as a missing file, because doing so would overwrite it with sample data. The user must repair the file or restore a backup before reopening Cindy.

Preference loading uses a different recovery policy: MainApp#initPrefs catches DataLoadingException and uses and saves default preferences. The shared null-root check also routes a preferences.json containing null through this existing fallback.

JsonUtilTest#readJsonFile_nullRoot_throwsDataLoadingExceptionAndPreservesFile checks the loading exception and unchanged file contents. MainAppTest#initModelManager_nullAddressBook_doesNotCreateSamplesOrOverwriteFile checks that invalid data does not trigger sample creation. MainAppStartupTest#startup_nullRootData_showsRecoveryAndPreservesFile checks the real JavaFX recovery dialog, disabled commands and file preservation in an isolated test process.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Help window

HelpContent provides an immutable list of CommandSummary objects in display order. Each summary contains a category, command word, description, syntax and a complete example. The catalog is independent of JavaFX and describes implemented commands.

HelpWindow renders each summary as a card, adding a heading whenever the category changes. HelpWindow.fxml keeps the User Guide controls outside the command reference's ScrollPane. The window is resizable, the scroll pane fits its content to the available width, and labels wrap without shrinking below their preferred height. HelpWindow.css uses Cindy's existing dark colors and typography. MainWindow retains one help window, shared by the help command, Help menu and F1 shortcut.

When adding or changing a command, update HelpContent and the User Guide's command summary together. Keep entries for each category contiguous and give each distinct command form its own entry with a unique syntax. Include a command form only when its behavior is implemented, and use a complete parsable command as its example. The short descriptions are maintained separately from command error messages so that the reference stays concise.

HelpContentTest checks command-family and parsed command-type coverage, unique formats, examples, category grouping and immutability. HelpWindowTest checks that the real FXML displays the catalog, wraps and scrolls at a small size, keeps the guide controls fixed, copies the URL and reopens without duplicating entries. See the manual help-window checks for entry-point and keyboard checks in the running application.

Command history

Each CommandBox owns one CommandHistory in the seedu.address.ui package. History belongs to the UI because recalling a command changes the input text without executing it. It does not change the Logic, Model or Storage interfaces. History is held in memory for the lifetime of the command box and is not restored after restarting Cindy.

Recording and navigation

CommandHistory is independent of JavaFX and owns a private List<String>, a navigation cursor and a saved draft. Its operations are:

  • record(String commandText): preserves nonblank text verbatim, skips consecutive identical entries and evicts the oldest entry before exceeding 50 commands. It resets navigation even when the entry is skipped.
  • previous(String currentText): captures the current draft when browsing begins and returns progressively older commands, stopping at the oldest. An empty history returns the current text unchanged.
  • next(String currentText): returns progressively newer commands, then the saved draft. When not browsing, it returns the current text unchanged.
  • resetNavigation(): ends browsing and discards the saved draft without changing recorded commands. The next previous call captures the current input as the new draft.

The cursor always lies between zero and the number of entries, inclusive. The position after the newest entry represents the draft. Bounds checks prevent navigation beyond the oldest entry or the draft, and callers never receive the mutable list. String arguments are checked with requireNonNull before state changes. Each instance is used on the JavaFX application thread.

Command box integration

On Enter, CommandBox ignores blank input and records other submissions before calling CommandExecutor#execute. Both parse failures and execution failures therefore remain available for recall. Successful execution clears the field; the existing ParseException and CommandException handling preserves failed input and shows its error style. The executor dependency is checked with requireNonNull during construction.

A KEY_PRESSED filter on the command text field handles plain Up and Down, replaces the text, positions the caret at the end and consumes the event. Modified arrow keys and other keys retain their normal behaviour, and other controls have no history filter. Recall never invokes the executor.

The text-change listener resets navigation when the user edits input. During recall, isRecallingCommand prevents programmatic text replacement from triggering that reset, so repeated Up/Down presses keep their position and saved draft. A finally block clears the flag after the update. The listener continues to clear error styling whenever text changes.

CommandHistoryTest covers the entry limit, ordering, duplicate handling, navigation boundaries, draft restoration, reset behaviour, null arguments and instance isolation. CommandBoxTest exercises real JavaFX controls and events for recall, Enter submission, failed commands, draft editing, blank input, modified keys and ordinary caret movement. See the manual command-history checks for checks in the running application.

Rescheduling an appointment

appointment --reschedule moves one of a client's appointments to a new date and time. The sequence diagram below shows how appointment --reschedule --id 2 --index 1 --date 2026-12-08 --time 18:00 is executed.

Parsing works like it does for delete in the Logic component section, so the diagram shows it as a single ref frame. The second ref frame reuses the client-selection interactions in the delete execution diagram; it ends once the selector has found the single client p. This keeps the rescheduling diagram focused on replacing the appointment. AppointmentCommandParser handles every form of the appointment command and picks the form from its flag (--add, --cancel, --reschedule, or --date/--week for listing). For --reschedule, it turns --id 2 (or --name NAME) into a PersonSelector and creates a RescheduleAppointmentCommand with the selector, the appointment index, and the new date and time.

RescheduleAppointmentCommand extends AppointmentIndexCommand, which extends PersonTargetedCommand, so the client is found the same way as for delete: the command gets the client list from the Model and asks the PersonSelector for the matching clients. In executeOn, the command checks that the client has an appointment at the given index, and that the new date is not in the past or more than a year ahead. It then creates a new Appointment at the new date and time, and checks that no other appointment of the client is at that date and time. Because Person and Appointment are immutable, the old appointment is not changed. Instead, Person#withAppointments returns a new Person whose list has the new appointment in place of the old one, and Model#setPerson replaces the client. The command then shows all clients in the list again, and LogicManager saves the data after the command returns. The new appointment is never cancelled, so rescheduling a cancelled appointment makes it active again.

The command fails with a CommandException (not shown in the diagram) if the index is not valid for the client, if the new date is in the past or more than a year ahead, or if another of the client's appointments is already at the new date and time.

Adding clients and detecting duplicate phone numbers

AddCommandParser accepts only --name and --phone. It identifies unsupported long flags using the quote-aware ArgumentTokenizer before validating field values, so --note after a valid phone is reported as an unknown parameter. Text after a closing quote, or text after a valid unquoted phone, receives an unexpected-text error with usage guidance. Quoted content remains subject to the field's normal validation.

Phone removes formatting separators for storage. Its equality and hash code use a comparison key that adds +65 to eight-digit local numbers; 81234567 and +6581234567 therefore compare equally while retaining their original country-code choice in value. Other country codes and number lengths remain distinct. Person#isSamePerson uses normalized name and phone equality to reject duplicate clients; AddressBook#hasPersonWithPhone uses the same phone equality for warnings when different clients share a number. These rules also apply when editing clients. Phone keyword searches still match digits in the stored value; they do not use the equality comparison key.

AddCommandParserTest covers unsupported flags and trailing text. PhoneTest and AddCommandIntegrationTest cover equality, hash codes, duplicate rejection and shared-phone warnings for both input orders.

Recording and editing sessions

SessionCommandParser creates an AddSessionCommand or EditSessionCommand with a client selector, date and note. Both commands create an updated immutable Person through withSessions and replace the client using Model#setPerson. Adding rejects a date already recorded for that client; editing rejects a missing session date and replaces only the note. An empty edit note clears the note without deleting the session. Session records do not have times or overlap checks.

Both commands return CommandResult(feedback, updatedPerson). MainWindow uses this updated client to display the detail panel immediately, including when a session command is run from the client list. Failed commands preserve the current panel. An ambiguous name lists the matching clients without changing session records. The profile shows only the four most recent sessions; editing an older record does not change its date or visibility. AddSessionCommandTest and EditSessionCommandTest verify both the updated model and the client returned for display.

Custom groups

A custom group, such as morning or rehab, is a Tag. The same Tag class is used for the built-in client types gym and personal, so a client's group memberships are simply their tags that are not client types (Tag.CLIENT_TYPES).

Group registry. AddressBook keeps every group in a LinkedHashSet<Tag>, separately from the clients. This lets a group exist before anyone is in it, so group --list can show empty groups. AddressBook keeps one invariant: every custom tag of every client is also in the registry. Whenever a client is added or replaced (addPerson, setPerson, setPersons), addGroupsOf adds that client's custom tags to the registry. A client therefore can never be in a group that does not exist, even if the data file was edited by hand. The registry is saved as a separate groups list in the JSON data file. A data file saved before groups existed has no such list, so its groups are rebuilt from the clients' tags when it is loaded.

Group names. ParserUtil#normalizeTagName trims the name, removes optional quotes, collapses repeated spaces and converts it to lower case, so Weight Loss and weight loss name the same group. Tag#isValidTagName then accepts words of letters and digits separated by single spaces or hyphens, up to Tag.MAX_LENGTH (50) characters. The length is checked before the regular expression runs, because a very long name would otherwise overflow the stack while matching.

Commands. GroupCommandParser picks the command from its flag:

  • group --name GROUP creates a GroupCommand, which adds the group to the registry.
  • group --list creates a ListGroupsCommand, which reads the registry and returns the group names in alphabetical order.
  • group --move ... --from GROUP --to GROUP creates a MoveGroupCommand.
  • group --delete --name GROUP creates a DeleteGroupCommand. tag --delete --group GROUP creates the same command.

tag --group (AddToGroupCommand), tag --untag (UntagCommand) and group --move (MoveGroupCommand) change one client, so they extend PersonTargetedCommand and find the client in the same way as delete. Each builds a new tag set, creates an updated client with Person#withTags and replaces the client with Model#setPerson. Adding a client to a group, or moving them into one, fails if the group is not in the registry, so typing mistakes do not create new groups.

The sequence diagram below shows how group --delete --name rehab is executed.

DeleteGroupCommand checks that the group exists, then calls Model#deleteGroup. AddressBook#removeGroup removes the group from every client in it before removing it from the registry, so the invariant above still holds afterwards.

DeleteGroupCommand, UntagCommand and MoveGroupCommand all end by showing every client again with updateFilteredPersonList(PREDICATE_SHOW_ALL_PERSONS). Without this, running one of them after find --group rehab would make the changed client disappear from the displayed list, which looks as if the client was deleted.

Alternative considered. We could store groups only as client tags, as AB3 does, without a separate registry. This was rejected because a group would then disappear as soon as its last client left it, and users could not create a group before adding clients to it.

GroupCommandParserTest, TagTest and ParserUtilTest cover parsing and name rules. GroupCommandTest, AddToGroupCommandTest, ListGroupsCommandTest, MoveGroupCommandTest, UntagCommandTest and DeleteGroupCommandTest cover execution, including the show-all-clients behaviour after find --group. See the manual group checks for checks in the running application.

Listing clients and today's appointments

list shows every client sorted by name, and list --today shows only the clients with a non-cancelled appointment today, earliest first. Both forms are handled by ListCommand. The sequence diagram below shows how list --today is executed.

Filtering and sorting. ModelManager wraps the FilteredList of clients in a SortedList. Model#updateFilteredPersonList(Predicate, Comparator) sets both at once. The one-argument updateFilteredPersonList(Predicate), used by list, find and most other commands, resets the order to sorting by name. list --today passes a predicate that keeps clients with a non-cancelled appointment today, and a comparator that orders them by their earliest appointment time today, then by name. The order stays until a command replaces the displayed list.

Today's date. ListCommand reads the date once, from a Clock, and uses it for both the filter and the feedback, so the result stays consistent even if the command runs across midnight. ListCommand.forToday(Clock) takes the clock as an argument, so the app passes the system clock and tests pass a fixed one that does not depend on the real date.

Feedback. For each client shown, formatScheduleLine lists that client's appointment times today, earliest first, followed by their name and ID, for example 07:00, 18:00 Alex Tanner (ID: 1).

Skipping the save. Command#isReadOnly() returns false by default. ListCommand overrides it to return true, because listing only changes which clients are displayed. LogicManager checks this before executing a command and does not save the data file after a read-only command. Listing therefore still works when the data file cannot be written, for example when it is read-only.

ListCommandTest covers filtering, cancelled appointments, sorting with ties, the feedback format and isReadOnly(). ModelManagerTest covers resetting the comparator, and LogicManagerTest checks that both forms of list succeed when saving would fail. See the manual checks for today's appointments for checks in the running application.

Appendix: Requirements

Product scope

Target user profile:

  • is a freelance gym trainer who trains many clients, at a gym or personally
  • needs to keep each client's contact details, notes, workout plan, sessions and appointments in one place
  • groups clients, e.g. by training time or goal, and needs to see which clients they are training today
  • prefers desktop apps over other types of applications
  • can type fast and prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: Keep every client's details, training records and appointments in one place, and find or update them faster than with paper notes, spreadsheets or a mouse-driven app, even between back-to-back sessions.

Use cases

(For all use cases below, the System is Cindy and the Actor is the trainer, unless specified otherwise.)

Use case: Add a client

MSS

  1. Trainer requests to view the client roster.

  2. Cindy shows the client roster.

  3. Trainer requests to add a client and provides the client's contact details.

  4. Cindy adds the client to the roster and confirms the addition.

    Use case ends.

Extensions

  • 2a. The client roster is empty.

    Use case resumes at step 3.

  • 3a. Trainer leaves out some required contact details.

    • 3a1. Cindy shows an error message stating which details are missing.

      Use case resumes at step 3.

  • 3b. Some of the given contact details are in an invalid format.

    • 3b1. Cindy shows an error message describing the expected format.

      Use case resumes at step 3.

  • 3c. The client is already in the roster.

    • 3c1. Cindy shows an error message stating that the client already exists.

      Use case ends.

Use case: List all clients

MSS

  1. Trainer requests to list all clients.

  2. Cindy shows all clients in the roster, sorted alphabetically by name, each with their client ID, name and phone number, along with the total number of clients.

    Use case ends.

Extensions

  • 1a. Trainer includes --today in the request.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. With 1000 clients loaded, list, find, view, edit and note should each complete within the two-second response limit in requirement 5, using the workload and timing method below.
  3. Trainers comfortable with keyboard input should complete at least three of the five tasks in the comparison below faster in Cindy than in a spreadsheet using mouse-based navigation. Compare the median of three correct attempts per task for each participant.
  4. All features are accessible using the keyboard.
  5. All commands should produce a result within 2 seconds.
  6. The user should not lose more than 1 minute of work after unexpected closure.
  7. The user should be able to understand the error message within 20 seconds of reading it.

Performance acceptance checks

These checks define acceptance criteria; they are not measured performance results. Record the Cindy revision, OS, Java version, processor, memory, storage type and participant details with the results so that a later run can use the same conditions.

Dataset and command response time (requirements 2 and 5). Use a disposable data file with 1000 clients, each with a unique name and phone number, a 100-character note, a 100-character workout plan, four appointments and four session records. Create two custom groups and put each client in one of them. Keep the data folder on writable local storage.

After startup, run one warm-up attempt of each command, then measure three attempts of each of the following: list all clients; find a client by phone digits; view a client by ID; change a client's phone number; and replace a client's note. Use known client IDs and valid, non-duplicate values. Restore the same starting dataset between attempts. Measure from pressing Enter until both the feedback and the resulting list or detail panel finish updating; for commands that change data, include the automatic save. Each measured attempt must finish within two seconds. Report the individual timings and any failures, rather than only an average.

Task completion time (requirement 3). Give each participant practice with Cindy and a spreadsheet containing the same 1000-client dataset, with one row per client and columns for ID, name, phone, note and groups. Record the spreadsheet application/version and the participant's typing speed and experience with both tools. In the spreadsheet, participants may type field values, but use the mouse to navigate, select records and apply filters. In Cindy, they use commands. Both tools must produce the same correct result for each task:

  1. Add a client with a supplied name and phone number.
  2. Find a client using supplied phone digits and report their full name.
  3. Replace a specified client's phone number.
  4. Replace a specified client's note.
  5. Show the clients in a specified custom group.

For each participant, time three attempts per task in each tool, using equivalent inputs and restoring the starting dataset between attempts. Alternate which tool goes first to reduce practice effects. Measure from revealing the task and its inputs until the correct result is visible, including time spent correcting errors. For each task, compare that participant's median time in each tool. Requirement 3 passes for that participant if Cindy is faster on at least three of the five tasks; ties do not count as faster. Report every participant's results.

Glossary

  • Appointment: A scheduled meeting with a client, identified by its date and time; managed using the appointment command
  • Client: A person who receives fitness coaching from a trainer and whose information is managed in Cindy
  • Client ID: A positive whole number that Cindy gives a client when they are added. It never changes, and it is never given to another client, even after the client it belonged to is deleted, unless all clients are cleared, which starts the numbering again from 1
  • Client record: The information Cindy stores about a client, including contact details, note, tags, workout plan, training sessions and appointments
  • Client roster: The collection of client records managed by a trainer in Cindy
  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Trainer: A freelance gym trainer who uses Cindy to manage clients
  • Training schedule: The collection of appointments arranged with clients
  • Training session: A dated session record for a client with an optional note, managed using session --add and session --edit; at most one record is stored per client per date

  3. Run tag --id ID1 --group morning, then run it again.
    Expected: The client is added to morning. The second command reports that the client is already in the group and changes nothing.
  4. Run tag --id ID1 --group rehab.
    Expected: An error says that rehab does not exist and suggests group --name rehab.
  5. Run tag --name check --group morning, then tag --name "other check" --group morning, then find --group morning.
    Expected: The first command lists both clients and asks you to choose one by ID, without adding either. The second adds Other Check. The search shows both clients.
  6. Run group --move --id ID1 --from morning --to evening, then close and reopen Cindy and run find --group evening.
    Expected: Group Check is in evening and no longer in morning; Other Check is still in morning. The groups and their clients are unchanged after reopening.
  7. Run the same move again, then group --move --id ID1 --from evening --to rehab and group --move --id ID1 --from evening --to evening.
    Expected: Each shows an error and changes nothing. The errors say that the client is not in morning, that rehab does not exist, and that the groups must be different.
  8. Run tag --id ID1 --untag evening, then group --list.
    Expected: Group Check is no longer in evening, but evening is still listed.
  9. Run find --group morning, then group --delete --name morning.
    Expected: Deleted group morning, and removed it from 1 client. All clients are shown again, Other Check is no longer in morning, and morning is no longer listed by group --list.
  10. Run group --delete --name morning, group --delete --name gym, then tag --delete --group evening.
    Expected: The first two show errors. The last deletes evening with Deleted group evening, and removed it from no clients.

Recalling commands

  1. Navigation, boundaries and draft restoration

    1. Prerequisite: Restart Cindy to begin with an empty history, then focus the command box.
    2. Type find --name Bob without pressing Enter, then press Up and Down.
      Expected: The input stays find --name Bob; no command executes.
    3. Replace the input with list and press Enter, then run find --name Alice.
    4. Type find --name Bob without pressing Enter. Press Up twice, then Up once more.
      Expected: The input changes to find --name Alice, then list, and stays at list. The displayed clients and result message do not change during recall.
    5. Press Down twice, then Down once more.
      Expected: The input changes to find --name Alice, then restores find --name Bob, and stays at find --name Bob.
    6. Press Up twice to recall list, then append edited. Press Down.
      Expected: The input stays list edited, because editing ended browsing. Up recalls the newest entry, find --name Alice; Down restores list edited. The stored list entry is unchanged.
    7. Recall list and press Enter.
      Expected: Only Enter executes the recalled command, the result shows the client list and the input clears. Up recalls list; Down restores the empty input.

  2. Failed commands and shortcut scope

    1. Submit not-a-command.
      Expected: An error appears and the failed text stays in the command box. Replace it with draft, press Up and then Down: the failed command is recalled and draft is restored.
    2. Hold Shift, Ctrl, Alt or Command/Windows while pressing Up or Down in the command box.
      Expected: No history entry is recalled. Plain Up still recalls the newest command.
    3. Focus the result display and press Up or Down.
      Expected: The command box text does not change.

  3. Capacity, duplicate suppression and session lifetime

    1. Restart Cindy, then submit find --phone 1, find --phone 2, and so on through find --phone 51. These valid searches change only the displayed filter, and history preserves their full text.
    2. Submit find --phone 51 again, then submit an empty input and an input containing only spaces.
    3. Press Up 50 times, then once more.
      Expected: The first recall is find --phone 51; the fiftieth is find --phone 2, and further Up presses stay at find --phone 2. The oldest command was evicted, and the duplicate and blank submissions used no entries.
    4. Close and reopen Cindy, focus the command box and press Up.
      Expected: The command box stays empty; the previous session's history is unavailable.

Saving data

Use a disposable copy of Cindy in its own folder. The data file is data/cindy.json in the folder containing the JAR.

  1. Saving after each command

    1. Run add --name "Save Check" --phone 91234567, then close Cindy using exit.
    2. Reopen Cindy.
      Expected: Save Check is still listed, with the same ID.

  2. Missing data file

    1. Close Cindy and delete data/cindy.json.
    2. Reopen Cindy.
      Expected: Cindy opens with the sample clients and creates a new data/cindy.json.

  3. Corrupted data file

    1. Close Cindy, back up data/cindy.json, then replace its contents with {"persons": [ and save it.
    2. Reopen Cindy.
      Expected: An error titled Unable to open Cindy says the client data could not be loaded and shows the file's location. Closing it closes Cindy without opening the main window. The file still contains {"persons": [.
    3. Restore the backup and reopen Cindy.
      Expected: Cindy opens with the clients from the backup.

  4. JSON null root

    1. Close Cindy, back up data/cindy.json, then replace its entire contents with null (without quotes) and save it.
    2. Reopen Cindy from a terminal with java -jar cindy.jar.
      Expected: The Unable to open Cindy recovery dialog appears and shows the data-file location. Closing it closes Cindy without opening the command window. The terminal does not report an uncaught NullPointerException, and data/cindy.json still contains null; sample clients are not written over it.
    3. Restore the backup and reopen Cindy.
      Expected: Cindy opens with the clients from the backup.
